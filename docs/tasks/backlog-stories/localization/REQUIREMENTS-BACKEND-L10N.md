## REQ-BE-1 — Язык-оригинал контента в публичной проекции (для GL-4)

### Что фронту нужно
Для каждой issue фронту нужно знать **язык, на котором история была подана автором** (язык-оригинал контента), чтобы пометить остальные локали `title/summary/description` как машинный перевод (решение D10), а не как дословные слова автора.

### Что наблюдаю сейчас (verified)
- Язык-оригинал **захватывается** на intake: `narrative.original_text`, `narrative.language`, `narrative.session_language` — [intake/contracts.py:31-35,236-245](../../../../../doge-complaints-gateway/src/core/intake/contracts.py#L31).
- Контент в публичной проекции отдаётся как i18n-объект `{et,ru,en}` — [projection/dto.py:15-18](../../../../../doge-complaints-gateway/src/core/projection/dto.py#L15).
- **Разрыв:** публичная проекция **не отдаёт** признак языка-оригинала (`grep original|locale|lang` по `dto.py` = 0). Данные есть в системе, но до фронта не доезжают.

### Требование (что должно появиться на границе)
- В публичной проекции issue фронту нужен **признак языка-оригинала контента** (напр. поле уровня issue вида `original_locale` со значением из множества поддерживаемых локалей).
- Значение должно соответствовать языку, который реально подавал автор (то, что сейчас лежит в `narrative.language`).
- Поле должно приходить и в списке (`/tallinn/issues`), и в одиночном (`/tallinn/issues/{id}`).

### Контракт со стороны фронта (как фронт будет это использовать / приёмка с FE-POV)
- Фронт читает `original_locale`; локаль, равную ему, показывает без маркера; остальные локали `title/summary/description` помечает «машинный перевод» (L10N-03).
- Если поле отсутствует/пустое — фронт деградирует мягко (не показывает MT-маркер), без падений. Т.е. поле желательно, но фронт не должен ломаться без него.
- Имя/форма поля — на усмотрение бэка; фронту важно лишь: **одно значение локали на issue, из согласованного набора локалей**.

### Открытый вопрос к бэку/аналитике
- Гарантируется ли, что одна из локалей `{et,ru,en}` контента **дословно** соответствует оригиналу (а не тоже переведена)? Для маркера «оригинал» это важно. Если оригинал хранится отдельно (`narrative.original_text`) и не обязательно совпадает с локалью в проекции — нужно решить, что считать «оригинальной» версией для UI.

## REQ-BE-2 — Анонимный приём телеметрии непереведённых меток (для GL-5)

### Что фронту нужно
Канал, куда фронт сможет **анонимно** сообщать факт «у метки нет перевода в словаре» (сработал humanize-fallback), чтобы оператор видел рост таксономии и докручивал переводы (решения D6/D11).

### Что наблюдаю сейчас
- На фронте телеметрии нет; humanize-ветка ничего не эмитит — [labelDisplay.js:25](../../../../src/i18n/labelDisplay.js#L25).
- Текущий принцип проекта — «no analytics/cookies» ([i18n-architecture.md](../../../i18n-architecture.md)); он **пересматривается** решением D11 (см. стори L10N-04).

### Требование (что должно появиться на границе)
- Эндпоинт-приёмник анонимных событий с минимальной полезной нагрузкой: **канонический ключ метки** + **локаль**, в которой не нашёлся перевод. Без PII, без идентификаторов пользователя/сессии.
- Приём должен быть устойчив к отсутствию/недоступности (фронт при недоступности sink делает тихий no-op).

### Контракт со стороны фронта
- Фронт шлёт событие только на humanize-miss; объём минимальный (ключ + локаль).
- Адрес sink: `{VITE_GATEWAY_BASE_URL}/telemetry/label-misses` (см. `resolveLabelMissSinkUrl` в [labelMissTelemetry.js](../../../../src/i18n/labelMissTelemetry.js)).
- Включение: `VITE_TELEMETRY_ENABLED=true` (по умолчанию выключено). Реализация — **L10N-04 Done (2026-06-16)**.
- Дедупликация в сессии вкладки; при ошибке сети — тихий no-op.
- Никаких куки/идентификаторов фронт не добавляет.

### Открытый вопрос к бэку/аналитике
- Где агрегировать и как показывать оператору «новые непереведённые ключи» (дашборд/лог) — на усмотрение бэка; фронту нужен только приём.

## REQ-BE-3 (FUTURE, не требуется сейчас) — Реестр таксономии меток

### Контекст
Решение D9 выбрало строить фильтр меток **из загруженных issue** (неполный список) и **отложило** полный реестр таксономии. Поэтому это **не требование на сейчас**, а зафиксированная будущая опция.

### Если/когда понадобится
- Фронту был бы полезен эндпоинт с **полным актуальным списком канонических ключей меток** (для полного, не «прыгающего» фильтра).
- До этого момента фронт сознательно живёт с неполным фильтром из данных (L10N-02). Возвращаться к REQ-BE-3, если неполнота фильтра станет проблемой для пользователей.
